# Benchmark-method audit

Reviewed the requested PowerShell benchmark methods and the API/runtime timing path on the current source checkout. Line numbers below refer to the checked-in files when this audit was written.

## Highest-impact findings

1. **Prefix reuse contaminates "prefill" rates.** `pi-stability.ps1` sends growing runs of the same `hello ` filler, ascending from 128 through 16,384 tokens (`tools/pi-stability.ps1:202-208, 308-317`). `context-sweep.ps1` does the same with repeated words, a fixed seed, and ascending context sizes (`tools/context-sweep.ps1:75-82, 91-96`). These requests share long identical prefixes; the scripts neither inspect `X-Flash-Gordon-Prefix-Cache` nor subtract reused context from the target. They may report suffix-only prefill throughput as if it were cold full-prompt throughput.
2. **Engine TPS is not end-to-end cost.** `src/api.c:2982-2986` defines prefill TPS as `prefilled_tokens / prefill_seconds` and decode TPS as `generated_tokens / decode_seconds`; the response headers repeat those values at `src/api.c:2990-3010`. `src/runtime.c:5688-5705, 5722-5739` excludes reused tokens from `prefilled_tokens` and starts the prefill clock only around the runtime prefill pipeline, not request parsing/rendering, HTTP queue delay, or time to first visible output. Decode timing starts after prefill and excludes queue/prefill latency (`src/runtime.c:5741-5806`). These are useful engine interval rates, but not client throughput or full-request latency.
3. **First-token measurements can count the wrong event.** `api-sse-keepalive.ps1` labels the first `data: ` SSE event as `first_data_ms` (`tools/api-sse-keepalive.ps1:46-51`); the API emits a role-only assistant chunk before generation (`src/api.c:2822-2845`), so that timestamp is not TTFT. `prefix-continuation-turn.ps1` estimates TTFT as engine prefill seconds plus decode seconds divided by completion tokens (`tools/prefix-continuation-turn.ps1:71-76`), which is not a client-observed first-token timestamp.
4. **Decode runs can stop before their requested token ceiling.** `context-sweep.ps1` asks for 32 tokens but never rejects a shorter generation (`tools/context-sweep.ps1:13, 71-80`). `pi-stability.ps1` checks the 32-token long-context run, but its short decode only logs the rate and does not check generated count (`tools/pi-stability.ps1:381-389, 393-397`). `qualify-openai.ps1` uses an exact short hello completion for every decode sample (`tools/qualify-openai.ps1:59-77`), so its measured generation is a correctness phrase, not sustained decoding. `api.c` only accepts `max_tokens`/`max_completion_tokens`; it does not parse `ignore_eos` or `min_tokens` (`src/api.c:1854-1876`), and the runtime breaks on EOS before incrementing generated-token count (`src/runtime.c:5752-5772`). A max-token setting is a ceiling, not a forced count.
5. **Repeated-prompt medians and max-of-runs are not cold, randomized samples.** `qualify-openai.ps1` warms and then repeats the identical hello prompt (`tools/qualify-openai.ps1:49-77`); `context-sweep.ps1` uses the same prompt again for prefill and decode (`tools/context-sweep.ps1:74-79`); `api-concurrent-probe.ps1` reuses one prompt across all four comparison runs and selects the best control/probe rate (`tools/api-concurrent-probe.ps1:109-132`). This rewards cache state and cherry-picks peak values rather than comparing representative distributions.
6. **No thermal-state control or tracking.** None of the benchmark scripts reviewed records board temperature, clocks, or a consistent idle/cooldown interval. The "stability" script checks rank liveness, not thermal stabilization (`tools/pi-stability.ps1:92-143, 250-260, 412-418`). Ascending, long-running runs can therefore conflate context effects with thermal/power state.
7. **Correctness gates are weak or absent.** `pi-stability.ps1` checks only two answers with substring matching (`tools/pi-stability.ps1:329-341`); `qualify-openai.ps1` checks one exact hello string but not a stored multi-prompt greedy baseline (`tools/qualify-openai.ps1:59-77`). `context-sweep.ps1` and the API probes do not check generation correctness. No reviewed benchmark hashes reference outputs or compares generated token IDs.
8. **The existing concurrency probe is not concurrent model throughput.** `api-concurrent-probe.ps1` runs one generation while four workers poll `/health` (`tools/api-concurrent-probe.ps1:42-59, 109-132`); this measures control-plane probe overhead, not two simultaneous generation streams. `api-probe-during-generation.ps1` similarly adds health/model traffic and starts a second queued chat with a 10-second client timeout (`tools/api-probe-during-generation.ps1:63-86, 119-148`). `api-queue.ps1` tests admission/cancellation policy, not per-stream/aggregate TPS (`tools/api-queue.ps1:7-17, 77-144`).

## Method-by-method notes

- **`tools/pi-stability.ps1`:** Soak sizes are produced by repeat heuristics, not token-count targets (`:202-208, 308-317`); the response does collect actual prompt tokens and engine headers (`:54-61, 311-326`). Reused-prefix hits are not asserted. The 4K perf value is taken from an earlier soak request after all smaller shared-prefix prompts (`:375-386`). Long 32K decode does assert 32 completion tokens, but the short decode does not (`:383-389, 397-410`). It has no repeat distribution, client TTFT, or thermal metadata.
- **`tools/context-sweep.ps1`:** Targets use `("hello " * repeats)` and an approximate character/4 calculation (`:63-66`), with a shared constant seed (`:44-50`). Actual prompt usage and engine timing headers are captured (`:52-60`), but target closeness, cache miss, and completion count are not acceptance conditions. The second request exactly reuses the first request's prompt (`:74-79`), and each larger context shares the preceding prompt prefix.
- **`tools/start-smoke-chat.ps1`:** This is a smoke/deploy gate, not a controlled benchmark. Its "cold" and "append" cases are a single tiny two-turn conversation (`:192-216`); it does correctly verify prompt accounting and cold/hit cache headers (`:203-213`) and checks one arithmetic answer (`:216`). The wall timer covers full request completion, but the displayed engine TPS has no repetitions, randomized prompts, or temperature normalization. The script writes transcripts and headers to a timestamped results directory (`:38-40, 179-186`).
- **`tools/qualify-openai.ps1`:** One default warm-up followed by five identical short exact-phrase responses (`:49-77`) yields a decode median for a handful of generated tokens. It correctly validates the text and median floor, but does not assert completion token count, bypass prefix reuse, collect client TTFT, track temperatures, or compare a fixed reference set. Its later tool-call checks validate API behavior, not performance.
- **`tools/api-abort-retry.ps1`:** The repeated prompt is deliberately reused for retry (`:34-40, 83-101`); it measures cancellation/recovery and cache-frontier preservation, not TPS. The prompt target is a `/4` character estimate (`:33-34`), and there is no generated-token/perf validation.
- **`tools/api-concurrent-probe.ps1`:** The "probes" are four periodic `/health` requests, not concurrent generations (`:42-59`). It approximates prompt length by characters (`:34-35`), uses one shared body across runs (`:36-41`), compares sequential controls then probe runs, and selects maximum values (`:109-132`), so cache/warm state and peak cherry-picking bias the result.
- **`tools/api-keepalive.ps1`:** Exercises raw HTTP persistence and error handling only; it has no model generation or benchmark denominator (`:5-8, 70-115`).
- **`tools/api-probe-during-generation.ps1`:** Prompt length uses the same rough character/4 fill (`:94-101`); added health/model probes and a busy chat perturb the generation being timed (`:103-148`). It records wall time and completion usage (`:168-186`) but no engine TPS or correctness.
- **`tools/api-queue.ps1`:** The long prompt is character-approximated (`:77-84`). It validates queue bound, cancellation, and FIFO/admission behavior; it records full wall and completion count only (`:146-197`), not performance rates.
- **`tools/api-sse-keepalive.ps1`:** This is an SSE/keepalive probe, not a throughput benchmark. Its prompt is character-estimated (`:31-33`); `first_data_ms` is the initial role chunk, not the first generated text (`:46-51`). It neither parses completion usage nor checks performance/correctness.

## API timing/accounting details

- Non-streaming responses expose prompt, prefilled, reused, completion, prefix-cache, and engine timing headers (`src/api.c:2990-3010`). The body usage reports actual prompt and generated counts (`src/api.c:2974-2978`).
- `X-Flash-Gordon-Prefill-TPS` counts only newly prefilled tokens; it excludes `reused_tokens` by design (`src/runtime.c:5691-5697, 5722-5739`). A reported high rate can therefore mean a short uncached suffix, not total prompt tokens divided by total prefill work.
- `X-Flash-Gordon-Decode-TPS` divides generated tokens by the engine's decode interval (`src/api.c:2985-2986`). That interval begins after prefill and includes callbacks/token decoding plus the decode dispatch loop; it is not client-wall throughput (`src/runtime.c:5741-5812`).
- Streaming responses currently send only SSE framing headers (`src/api.c:2362-2391`) and chunks/end events without `usage` or `X-Flash-Gordon-*` timing headers (`src/api.c:2822-2845, 2851-2900`). Any streaming harness must pair with a non-stream request for usage/engine metrics, or explicitly report those fields as unavailable.
- The runtime tests for EOS before emitting/incrementing the completion count (`src/runtime.c:5752-5772`); generated token counts are not necessarily equal to `max_tokens`. No parsed `ignore_eos`/`min_tokens` controls exist in `src/api.c:1578-1601, 1854-1876`.
